# Domain drafters, EAGLE grid (canvas A3)

Branch `experiment/domain-drafters-eagle`, started 2026-11-20.

## Question

How does fine-tuning the 8B drafter on one domain change its speed **in that
domain** and on **everything else**, the generalist open-perfectblend (OPB)
traffic included? And does an equal-budget mixed fine-tune keep most of the
in-domain gain without the forgetting?

EAGLE is the more sensitive drafter here. With the same 8k multilingual traces
and recipe, EAGLE e10's development acceptance rose 1.66 → 2.42 (+46%) and k3/C1
serving throughput rose 17%. DSpark e10 rose only 3.84 → 4.14 (+7.8%) and +4.6%.
See [drafter-updates.md](drafter-updates.md) and
[dspark-adaptation.md](dspark-adaptation.md). A sibling branch
(`experiment/domain-drafters-dspark`) runs the same grid for DSpark.

## Design

| item | setting |
| --- | --- |
| start | EAGLE 3.1 e10 thinking-off, served export: HF `faruk-zahiragic/Apertus-v1.5-8B-EAGLE3.1-e10-thinking-off` @ `4c9d4c9e`, SHA256SUMS verified (`model.safetensors` 42b05496…). The trainer checkpoint `checkpoints/best` (step 251,955) was emptied by the scratch cleaner, so `model.init_from` now also accepts an export: keys are mapped back with TorchSpec's `to_internal_keys`. Only the tensors that `export_head` drops (embedding, vocab maps) are filled from the fresh draft, and the frozen lm_head must still equal the target's. |
| arms | math, code, chat, summarization, multilingual, tool (tool use; the data branch's name for the structured domain) (one head each) + **mixed** (8,000 rows: 1,334 or 1,333 of each domain's first rows, interleaved) |
| data | Target-answered traces from the sibling data branch: 8,000 train / 256 dev per domain, thinking off, deployment sampling. Contract: `spec-exp-data/domain-drafters/traces/<domain>/{train,dev}.jsonl` |
| recipe | Identical for every arm = `adapt-mult-n8k-r0`: 1 node (4 ranks), 32 rows/step, constant LR 3e-5 after 19 warmup steps, 384 steps (12,288 rows, ~1.5 epochs of 8k), forward KL, TTT 7, seed 1, final checkpoint exported |
| budget | Equal **rows** per arm, as in T5. Token budgets differ by domain (summarization rows are long); report tokens per arm with the result. |
| offline matrix | Each run evaluates its own dev set (`eval_data`) and the other five dev sets plus OPB held-out (first 512 of e10's 2,000 rows; `extra_eval`) every 64 steps. The step-0 eval is the e10 baseline row, and the final eval is the arm's row. The metric is simulated acceptance length (7 rollout steps): a trainer quantity, not served acceptance. |
| OPB held-out | Rebuilt from the colleague's corpus + `val_ids.txt` in corpus order (`methods/eagle/launch/domain/opb-heldout.sh`): 2,000 rows from the first 19,314, sha256 4293a420… |

**Headline.** Diagonal gain (own domain, adapted − e10) against the
off-diagonal and OPB change, per arm, plus the mixed arm's row.

**Serving confirmation (queued after the matrix).** Each head is compared with
e10 on its own domain, OPB and one far domain, at k=3/k=7 and C=1/C=64. This
uses the existing GPU-swapped harness and calibrated correctness gate from
drafter-updates. Benefit rule (unchanged): at least 10% more throughput **and**
at least 10% lower median TPOT in both swaps. Forgetting is material if OPB
drops by more than 2%.

**Limits.** Single seed; one LR (3e-5, low relative to e10's 1e-4 peak); fixed
row budget; trainer acceptance is not serving speed.

## Running it

On a Clariden login node, from the cluster checkout
`/iopsstor/scratch/cscs/faruk_zahiragic/spec-exp/domain-eagle`:

```
methods/eagle/launch/domain/submit-grid.sh status   # READY markers
methods/eagle/launch/domain/submit-grid.sh pilot    # 4-step smoke on the pilot slice
methods/eagle/launch/domain/submit-grid.sh full     # 7 one-node jobs, 4 h limit each
```

Configs are generated by `methods/eagle/launch/domain/make-configs.py` into
`methods/eagle/configs/8b/domain/`. Runs land in
`spec-exp-data/domain-drafters/eagle/{runs,heads}` and are backed up to
`/capstor/scratch/cscs/faruk_zahiragic/domain-drafters-backup/eagle/`.
