Plain Apertus 1.5 8B holds about 1,840 output tokens/s, then the KV cache fills

Closed-loop load sweep of one plain target on a single GH200. Throughput stops climbing once prefill dominates. Past 256 concurrent summarization requests the cache is full, extra requests only wait, and the engine starts evicting work.

Load sweep

128 untouched summarization prompts, about 3.8k prompt tokens and 200-token answers, natural end-of-sequence. Closed loop: exactly C requests open, 4×C requests per level (at least 32). The client ran on the replica node, not a login node. Every request succeeded. GPU utilization was 100% under load, peak power 531 W.

Reading

  • Throughput saturates near 1.84k output tokens/s from C=128. Prompts are ~3.8k tokens, so the GPU spends most of its time on prefill. Raising concurrency from 128 to 512 adds about 30 tokens/s and multiplies time-to-first-token.
  • The KV cache fills at C=256. At most 167 requests fit. The rest queue. Preemptions start here (40, then 66 at C=512).
  • A queue appears earlier than a full cache. Waiting requests show up at C=32, while the pool is still only 22% full, because prefill of these long prompts cannot keep every open request on the GPU at once.

Caveats

One workload shape

Long prompts, short answers. Chat and code prompts are shorter, so more of them fit before the pool fills. Rerun with LOADTEST_WORKLOAD=chat or code.

Closed loop, not an arrival rate

The client holds exactly C requests open. Real traffic arrives at a rate. An open-loop test, requests per second, is the next step for a capacity number you can quote against a service target.

Two earlier sweeps on the same day were invalid

Job 3546229 was capped at 100 connections by the client pool, so the server never saw C=128 or C=256. Job 3546292 aborted on a keep-alive race. Both are fixed in the harness. This page is job 3546378.
