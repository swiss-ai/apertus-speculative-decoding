## Goal and recipe

Train a DSpark speculative-decoding drafter for Apertus-v1.5-70B the way Yu
(colleague) trained the 8B one (`docs/CONFIG_DSpark_Apertus_1.5_8B_09_29.md`):
speculators trainer, DSpark 5 layers, block 8, Markov rank 256, confidence head
with Markov input, loss CE 0.1 + TV 0.9, Muon, 10 epochs, thinking off, on
open-perfectblend with every answer regenerated by the target (70B here).
70B-forced changes: target layers `1 20 39 58 77`, `--fsdp-shard` (the drafter
has ~6B trainable parameters), and a TP2 vLLM extraction server per node.

## Task 1: one-node training run on Beverin (start now)

The user wants this run even though it is slow: Clariden is not expected to free 16 nodes soon.

- **Layout:** 1 node, TP2 extraction on GPUs 0,1, 2 FSDP trainer ranks on GPUs 2,3. Data `/iopsstor/scratch/cscs/faruk_zahiragic/apertus-dspark70b/data`, run id `opb-thinkoff-1n-beverin`, 10-epoch schedule.
- **Batch:** 2 ranks × `SEQ` 8192 × `ANCHORS` 512 = 16,384 tokens per step, a quarter of Yu's 65,536. Keep `SEQ` at 8192 so the longest conversations are not cut. speculators 7046ac6 has no gradient accumulation, so this run's batch cannot match Yu's or Clariden's.
- **LR:** Yu used 3e-4 at 65,536 tokens. Square-root scaling to a quarter of the batch gives 1.5e-4. That is a suggestion; confirm the value with the user before the long run.
- **Expected speed:** ~5–6 s per step at this batch (only measured at `SEQ` 4096: 4.6 s), so ~8 days per epoch and ~80 days for 10 epochs. Report the real step time after the first job.
- **Memory risk (the main one):** the 1-node smoke at `SEQ` 4096 used 473–483 of 501 GB, and one epoch-end save stalled at 499 GB while another was OOM-killed. Rank 0 gathers the full state on the host when it saves.
  - Before the long run, do a short 1-node pilot at `SEQ` 8192 that forces an early save and a resume, logging memory every 10 s (`submit-train.sh` already does this).
  - If it is too tight, lower `EXTRACT_MEM`, `WORKERS`/`PREFETCH` (defaults 4/2) and the save frequency, or move the extraction server's KV cache down.
  - Do not change the recipe silently; report what you change.
- **Then:** chain 24 h jobs (`CHAIN`), checkpoints ~every 1/64 epoch so a lost job costs little, and check after each job that steps advance (log `global_step`) and that resume works.

## Task 2: debug multi-node training on Beverin (in parallel)

Symptom: from 2 nodes up, a step takes ~180–200 s, against ~4.6 s on 1 node. The time sits in backward (FSDP reduce-scatter) and Muon (redistribution of sharded weights), in both all-gather and all-to-all mode.

What is known:
- Isolated RCCL benchmarks on reused buffers reach ~68 GB/s for all-reduce, all-gather and reduce-scatter, and ~20 GB/s for all-to-all (jobs 693943, 693944).
- With a fresh buffer per call they drop to 6–9 GB/s (jobs 693957–693960).
- Three settings did not help: `OFI_NCCL_DISABLE_DMABUF=1`, `FI_MR_CACHE_MONITOR=disabled`, `PYTORCH_HIP_ALLOC_CONF=expandable_segments:True`.
- Suspected cause: registering GPU memory with the network on MI300A. That does not explain the ~50× gap.
- SIGUSR1 stack dumps did not reach the trainer log.

Do these three, using small 2-node jobs (≤1–2 h each, record every job id):
1. **Profile a 2-node run.** Use `NCCL_DEBUG=INFO NCCL_DEBUG_SUBSYS=NET,REG,COLL` (RCCL reads the NCCL_* names), the torch profiler on a few steps, or both. Find which collective is slow and why: protocol, chunking, registration, fallback to host/TCP.
2. **Try fixes:**
   - FSDP gradient reduce-scatter in bf16 (`MixedPrecisionPolicy(reduce_dtype=bf16)` in speculators' `apply_fully_sharded`).
   - RCCL protocol and channel settings (`NCCL_PROTO`, `NCCL_MIN_NCHANNELS`, `NCCL_NCHANNELS_PER_NET_PEER`).
   - The aws-ofi plugin's host netstack with the rocm6 plugin build instead of the rocm7 artifact.
   - Measure each change's step time.
3. **CSCS support.** Draft a ticket for the user: the symptom, the benchmark numbers above, job ids, image and plugin versions, and what was tried. Give the user the text; don't send it yourself unless the user asks.

When a fix brings multi-node step time near the 1-node rate, report to the user before scaling up. A multi-node run would then replace or join the 1-node run. Keep the 1-node run going meanwhile, and keep Task 2 jobs from starving it (small jobs, separate run ids).
